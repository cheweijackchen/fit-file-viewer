# Design Map 撰寫指南

> 說明如何為 .pen 設計稿建立 Design Map 文件，  
> 讓 AI 在協作修改時能快速理解設計結構，  
> 而不需要每次重新探索節點樹。

---

## 為什麼需要 Design Map？

**問題：**

AI 無法直接讀取 `.pen` 檔案（加密格式）。它只能透過 MCP 工具查詢節點，但單次查詢往往回傳整份文件的資料，需要大量解析才能定位特定元素。

**後果：**

- 每次對話，AI 都要重新「探索」設計稿結構，耗費大量時間
- 你說「左側欄的 Day 項目」，AI 不知道對應哪個 node name
- 從截圖能看出視覺，但無法反推節點路徑

**Design Map 的作用：**

建立一份對照表，把你平時用的功能語言（UX 語言）對應到設計稿的節點命名。  
有了這份文件，你只需要說「修改 Main Graph Expanded 左側欄的 Day 副標題」，AI 就能直接找到目標。

---

## 文件格式

### 1. 標頭

```markdown
# [設計名稱] Design Map

- 設計檔: `design/pages/xxx.pen`
- 最後更新: YYYY-MM-DD
```

---

### 2. 功能概覽（給人看）

1-3 句話說明這份設計的**用途**和**主要使用情境**。  
不需要列出所有功能，只需傳達「這份設計在做什麼」。

```markdown
## 功能概覽

Trail Planner 讓使用者逐日安排登山路線節點。  
主畫面分為三個區域：左側 Day 列表、中間路線建構區、右側海拔圖表。  
使用者從左側新增 Day、在中間選擇路線節點，右側即時更新預估時間與海拔資訊。
```

---

### 3. Frame 清單（設計狀態對照）

列出設計檔裡的每個 Frame，說明它代表哪種畫面狀態或使用情境。

```markdown
## Frames

| Frame 名稱                  | 描述                              |
|----------------------------|-----------------------------------|
| Main — Graph Expanded      | 主規劃畫面，右側圖表展開            |
| Main — Graph Collapsed     | 主規劃畫面，右側圖表收起            |
| Trail Selection            | 進入 Planner 前的行程選擇畫面       |
| Landing — Has Trips        | 已有行程的首頁狀態                  |
```

---

### 4. 區塊地圖（給 AI 看）

這是 Design Map 的核心。格式：**你會怎麼說 → node name**，附簡短功能說明。  
每個 Frame 獨立一個區塊，只記你可能提及的區域，不需窮舉所有節點。

```markdown
## 區塊地圖

### Main — Graph Expanded

**左側欄** (`sidebar`)

| 你會說...         | Node Name              | 說明                        |
|------------------|------------------------|-----------------------------|
| 左側欄整體        | `sidebar`              | Day 列表容器                 |
| Day 列表項目      | `day1` / `day2` / ...  | 每個 Day 的列表行             |
| Day 的日期名稱    | `day1Info` 內第一個 text | 顯示「Day 1」等文字           |
| Day 的副標題/提示 | `day1Info` 內第二個 text | 顯示狀態提示，如「Empty」     |
| Day 右側的圖示    | `day1` 內的 icon_font   | 箭頭或勾選圖示               |

**Day 項目狀態**

| 狀態             | 視覺                  | 副標題文字範例  |
|-----------------|----------------------|----------------|
| 目前編輯中       | 深綠底色              | —              |
| 已完成（有資料） | 淺綠底色 + 勾選圖示   | "3h 20m"       |
| 空白未編輯       | 淺綠底色              | "Empty"        |

**中間面板** (`center`)

| 你會說...     | Node Name       | 說明                    |
|-------------|-----------------|-------------------------|
| 面板標題     | `centerTitle`   | 顯示目前編輯的 Day 名稱   |
| 起點選擇列   | `startRow`      | Starting Point 下拉選單區 |
| 當前節點卡片  | `nodeCard`      | 顯示目前選取的路線節點    |
| 鄰近節點列   | `neighborsRow`  | 可選擇的下一個節點        |
```

---

### 5. 通用元件（選填）

若有跨 Frame 重用的元件，在此列出。

```markdown
## 通用元件

| 你會說... | Node Name   | 出現位置              |
|----------|-------------|----------------------|
| 下拉選單  | `dropdown`  | startRow、各篩選欄位  |
| 新增按鈕  | `addBtn`    | sidebarHeader、工具列 |
```

## 核心原則

### ✅ Do's

- **用功能語言命名 node**（`startRow`、`dayInfo`），讓名稱和你描述需求的語言接近
- **記錄元件的所有狀態**：同一元件的不同視覺狀態（空白、已完成、選取中）要列表說明
- **保持術語一致**：文件裡的詞彙要和你跟 AI 對話時用的一樣
- **只記你會提及的區塊**：覆蓋「你用功能語言說得出來」的部分就夠了
- **更新時機**：新增或移除 Frame、或區塊結構大幅重構後再更新

### ❌ Don'ts

- **不要記錄 node ID**（如 `8nED7`）：ID 在元素被複製或重建後會失效，不具長期可靠性
- **不要記錄顏色、padding、字體大小**：AI 從截圖讀視覺細節，文件不需要重複
- **不要窮舉所有節點**：Design Map 不是 node tree，只記有語意的區塊
- **不要把功能規格寫在這裡**：功能規格放 story 文件，Design Map 只做結構對應

---

## 與 AI 協作的工作流程

**對話開始時：**

> 「請先讀 `docs/design-maps/hiking-trail.md`，再截圖看一下 [Frame 名稱]。」

AI 有詞彙對應 + 視覺確認，就能直接操作，不需要重新探索節點樹。

**描述修改位置時，優先用（由精確到模糊）：**

1. **在 Pencil 選取節點** → 告訴 AI「我選好了」，AI 用 `get_editor_state` 讀取
2. **Frame + 區塊 + 元件**：「Main Graph Expanded 左側欄 Day 1 的副標題文字」
3. **功能描述**：「已完成的 Day 項目的提示文字」（需對照 Design Map）
